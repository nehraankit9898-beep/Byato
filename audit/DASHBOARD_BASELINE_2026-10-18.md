## Intended metric definitions inferred from code and schema

- Dashboard customer total: active customers only (`Customer.status = ACTIVE`).
- Marketing opt-in: active customers with `marketingConsent = true` and `optOut = false`.
- Opted out: currently counted by the dashboard route without an active-status filter; this requires reconciliation with the active-customer denominator.
- Visits and repeat customers: `Visit` rows grouped by customer; the current route does not filter visits through active customers.
- Visit trend: 14 calendar days generated by the server, currently using server-local/UTC date operations rather than the hotel timezone.
- Campaign analytics: campaign-message statuses/timestamps and booking attribution; live segment and consent data are loaded separately from all customers.
- Owner sales report: the route documents [start, end) tenant-local business-day semantics and uses `zonedDayBounds`.

## Static hypotheses requiring reproduction

1. **Dashboard trend timezone mismatch:** the stats route builds day boundaries with server-local `Date` methods and emits UTC date keys, while hotel reports use the hotel IANA timezone and the client formats date-only keys in the browser timezone. A visit around midnight can appear on the wrong day or outside the 14-day window.
2. **Dashboard consent denominator mismatch:** `totalCustomers` and `marketingOptIn` filter active customers, but `optedOut` does not. This can make the consent chart and no-consent count disagree with the displayed active-customer total.
3. **Dashboard/analytics population mismatch:** the dashboard uses active-only customers for some metrics, while analytics segment sizes and consent health load all customer statuses. The intended archived/inactive-record policy needs one consistent definition.
4. **Owner Reports failure masking:** `ReportsView` renders zero-valued cards and an empty payment message whenever the report query has no data, including an API failure; it has no report loading/error/retry state.
5. **Owner Reports schedule parsing/render risk:** `ReportsView` calls `JSON.parse(schedule.recipients)` during render and in a mutation handler without a safe fallback. A malformed persisted value can crash that view. Its frequency state also starts at `DAILY` even when the stored schedule is `WEEKLY`.
6. **Dynamic client-rendering risk:** dashboard greeting/date formatting uses current time and browser-local formatting. This must be checked against Next.js server pre-render/hydration behavior and fixed only if reproducible.

These are hypotheses, not final findings. No fake data, environment value, production migration, or destructive database command was used.
